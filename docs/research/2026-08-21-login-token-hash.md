# כשל הכניסה במובייל: הקוד מוכן, ההגדרה בדשבורד היא הקובעת (21.8)

**השאלה:** קישור כניסה שנפתח בדפדפן אחר מזה שביקש אותו (נחיתה בדפדפן של פייסבוק,
פתיחה מאפליקציית Gmail) נכשל עם הודעה מטעה. האם זה תיקון קוד או תיקון הגדרה?

**התשובה: תיקון הגדרה בלבד. אפס שינויי קוד נדרשים.**

## מה נמצא בקוד

שני מסלולי אימות בנויים ועובדים במקביל, ומה שקובע איזה מהם פעיל הוא תבנית המייל
בדשבורד של Supabase, לא הקוד:

- **מסלול code (PKCE), תלוי-דפדפן:** `signInWithOtp` עם `emailRedirectTo` שמצביע על
  `/auth/callback` (`src/app/login/use-login.ts:29-34`). כשהתבנית בדשבורד היא ברירת
  המחדל (`{{ .ConfirmationURL }}`), הקישור עובר דרך שרת ה-verify של Supabase וחוזר
  עם `?code=`, ו-`exchangeCodeForSession` נזקק ל-code verifier שיושב ב-cookie **רק
  בדפדפן שביקש את הקישור**. פתיחה בדפדפן אחר = אין verifier = כשל. ההערה בקוד
  (`src/app/auth/callback/route.ts:17-18`) מזהה את התרחיש במפורש.
- **מסלול token_hash, עובד בכל דפדפן:** `/auth/confirm` קורא
  `verifyOtp({ type: "email", token_hash })` צד-שרת (`src/app/auth/confirm/route.ts`),
  בלי שום תלות במצב דפדפן קודם: מגן מ-open-redirect, יוצר שורת משתמש עם ריפוי עצמי,
  רושם אירוע login. מכוסה בבדיקות אופליין (`tests/auth-handlers.test.ts:31-69`).

## מה לבדוק ולשנות בדשבורד (להב או המייסד)

Authentication -> Emails (Email Templates). **שתי תבניות, לא אחת:** "Magic Link"
(משתמש קיים) וגם "Confirm signup" (משתמש חדש - `signInWithOtp` אצלנו לא מעביר
`shouldCreateUser`, ולכן המייל הראשון של משתמש חדש יוצא מתבנית ה-signup).

בשתי התבניות, להחליף את ה-href של הקישור ל:

```
{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=email
```

ולוודא ש-Site URL (Authentication -> URL Configuration) מוגדר לדומיין הפרודקשן -
`{{ .SiteURL }}` נגזר ממנו. אין להוסיף `next={{ .RedirectTo }}`: זה URL מוחלט,
ו-`sanitizeNextPath` (`src/server/api/auth-handlers.ts:6-10`) יפיל אותו ל-"/" ממילא.

**איך יודעים מה המצב היום בלי דשבורד:** שולחים קישור לעצמנו ובודקים לאן הוא מצביע.
`https://<ref>.supabase.co/auth/v1/verify?...` = המסלול הישן;
`<site>/auth/confirm?token_hash=...` = המעבר כבר בוצע.

## קוד 6 ספרות - נדחה לשלב ב

המעבר לתבנית סוגר את הכשל המדווח. קוד `{{ .Token }}` מוקלד עדיין מוסיף ערך בשלושה
תרחישים שגם token_hash לא פותר: סורקי קישורים של ספקי מייל ששורפים קישור חד-פעמי
(Outlook SafeLinks), קריאת המייל במכשיר אחד והתחברות באחר, ושכתובי קישורים ארגוניים.
אבל הוא דורש UI (שדה קוד + `verifyOtp({ email, token })` בלקוח). ההחלטה: קודם המעבר
בהגדרה, ורק אם הכשלים ממשיכים - בונים את הקוד.

## הודעת הכשל

היום שני המסלולים נופלים לאותו `/login?error=link` ("קישור הכניסה פג או כבר שומש") -
מטעה בתרחיש הדפדפן-האחר. אחרי המעבר לתבנית ההודעה הופכת מדויקת מעצמה: מצבי הכשל
שנותרים הם באמת פג-תוקף או שימוש-קודם. לא נדרש שינוי קוד.
